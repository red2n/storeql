# StoreQL — Independent Deep-Dive Audit

**Scope:** A fresh, from-scratch assessment of the *actual* code on disk — no prior audit or its finding IDs were consulted. Every claim below was verified by reading the referenced file(s), not inferred from docs.
**Method:** Traced the trust boundary (gateway → services), object- and role-level authorization on every reachable path, SQL/locking/money handling, the Kafka publisher↔consumer map, list-endpoint pagination, inter-service client resilience, and the Flutter client's storage + error surfaces.

## Executive verdict

The cross-cutting foundation is genuinely solid: the gateway is the single public door, it **strips client-supplied identity headers and re-stamps only JWT-verified ones**, refuses to boot on a weak JWT secret, and services take `tenant_id` exclusively from those verified headers. Writes are **default-deny** by role, money is `BigDecimal`/`NUMERIC`, and inter-service clients carry timeouts (mostly with retry/circuit-breaker). This is a well-built system.

**Two distinct bug classes rise above "quality debt": [F1]/[F8]/[F9] (object-level read authorization) and [F12] (Bean Validation cascading).** Both share a shape worth naming: a control existed and looked correct from the outside, but didn't actually fire on every path it needed to.

F1/F8/F9 are the same broken **object-level** authorization gap, found three times: role-based (tenant/write) checks are strong, but a per-record ownership check was missing on reads. F1 was on order-svc (`GET /orders/{id}`, including delivery address and contact phone); F8 is the identical gap on customer-svc (`GET /customers/{id}` and its addresses/loyalty/store-credit sub-resources); F9 is the same gap one hop indirect on payment-svc (`GET /payments/{id}` and by-order tenders/refunds, ownership resolved via order-svc). Each was found by checking whether the prior fix's pattern had been swept to the next service — it hadn't, until now. All three are fixed (`OrderService`/`CustomerService`/`PaymentService`.`requireReadAccess`); purchase-svc was also checked and has no analog. The sweep of all 12 services for this shape is now complete.

F12 is a different mechanism with a similarly wide reach: `Validations.validate(req)` was being called correctly on several critical write endpoints — including `POST /orders`, the primary checkout path — but Jakarta Bean Validation does not cascade into a `List<...>` field's elements without an explicit `@Valid` on that field, and none of the 13 nested-list DTOs across 5 services had it. A customer JWT (no staff role required — `POST /orders` is on the gateway's guest/customer whitelist) could place an order with a zero or negative quantity and have it sail through every layer: Bean Validation (silently non-cascading), the service layer (no manual check), and the database (no `CHECK` constraint). All 13 sites now cascade correctly; 5 endpoints that skipped validation entirely also got real `Validations.validate()` calls (one further candidate, `importSupplierCsv`, turned out to already have an equivalent manual check on closer reading).

Everything else is maintainability / scale-tail / consistency work.

## Verified-strong foundation (re-checked fresh, not gaps) ✅

- **Trust boundary.** `platform/gateway/.../filters/JwtAuthFilter.java` strips any inbound `X-Tenant-Id`/`X-User-Id`/`X-Roles`, validates the Bearer JWT (RS256 only, against the key set iam-svc publishes, + issuer — since 20.15 the gateway holds no signing secret), and re-injects identity from claims only. Guest storefront access is a tight path whitelist keyed off `X-Storefront-Tenant`.
- **Authorization default-deny (writes) — and one detail the original audit undersold.** `shared/common-web/.../AdminAuthorizationFilter.java` denies every mutating request without a staff role unless the path is on an explicit bootstrap/identity/guest allowlist. Re-reading the filter's `filter()` method directly (not just its own javadoc, which reads as write-focused): `requiresManagement(path, method)` — the check backing "`/admin/**` requires a management role" — is evaluated **before and independent of** `isMutating(method)` (`AdminAuthorizationFilter.java:64,141-151`). So `/admin/**` is actually gated for **every** HTTP method, GETs included, not just writes. This is exactly why F1/F8/F9/F10 (below) could only happen on paths that *aren't* under `/admin/` — `/orders/{id}`, `/customers/{id}`, `/payments/{id}`, `/customer-vat-status/{id}` — and why **reporting-svc** (checked here since the original audit named it only in the service-count snapshot, never in a finding) turns out clean without needing a fix: both its resources (`AdminResource`, `SalesReportResource`) live entirely under `/admin/reports/**`, so every read already requires `PLATFORM_ADMIN`/`OWNER`/`MANAGER` for free, and both correctly source `tenantId` from `TenantContext`, not the request.
- **No direct service exposure.** In `docker-compose.yml` only `gateway` and the UI publish host ports; Postgres/Kafka/Consul/Redis are internal or loopback-bound.
- **Money & concurrency.** `BigDecimal`/`NUMERIC` throughout; reserve/deduct locks rows `FOR UPDATE`; checkout is idempotency-key gated.
- **Client resilience.** Every `*/client/*.java` sets a request `@Timeout`; the order/payment clients add `@Retry` + `@CircuitBreaker`/`@Fallback`.
- **SQL safety rules (`docs/coding-standards.md` §1) — checked here since the Method line claimed this but the original findings showed no evidence.** Zero `SELECT *` anywhere in `services/*/src/main/java` or `shared/*/src/main/java`. Every `UPDATE`/`DELETE` statement carries a `WHERE`; the one multi-line case worth a second look (`InventoryRepository.computeRopPlans`, a ROP/EOQ recompute joined against a demand-history subquery) has its `WHERE rp.tenant_id=? AND rp.store_id=?` on the outer statement, correctly tenant-scoped and parameterized.
- **Golden rule #8 (append-only tables) — also checked here, also claimed but unevidenced originally.** No `UPDATE`/`DELETE` at all against `order_status_history`, `payments`, `loyalty_ledger`, or `audit_log`. `stock_movements` has exactly one `DELETE` (`InventoryRepository.java:3554-3576`), and it's a deliberate, self-documented archive-then-purge: `INSERT INTO stock_movements_archive ... SELECT ... FROM stock_movements` followed by `DELETE FROM stock_movements WHERE tenant_id=? AND created_at < ?` in the same transaction — data is relocated, not lost, and the code comments cite rule #8 directly. `refund_tenders` (payment-svc) has zero `UPDATE`/`DELETE` — insert-only.
- **Golden rule #6 (outbox: event + DB write atomic) — also checked here, also claimed but unevidenced originally.** `shared/common-service/.../BaseOutboxRepository.insertOutbox(Connection c, OutboxRow o)` takes an already-open connection, so it's structurally impossible to call outside a transaction. Spot-checked `CustomerRepository.createCustomer` and `PaymentRepository.createTender`: both call the business `INSERT` and `insertOutbox(c, event)` inside the same `inTx(...)` closure (single commit/rollback boundary, `BaseJdbcRepository.inTx` at line 52-71). All 10 repo files that call `insertOutbox` also use `inTx`.
- **Golden rule #7 (idempotent consumers) — also checked here.** Shared mechanism: `BaseJdbcRepository.markProcessedIfNewTx(Connection c, UUID eventId, String consumer)` does `INSERT INTO processed_events (event_id, consumer) VALUES (?,?) ON CONFLICT (event_id) DO NOTHING`, called with the caller's own connection so the dedupe mark commits atomically with the business effect (same pattern as rule #6). `eventId` is a globally-unique `UUID.randomUUID()` minted once per event at the producer (`events-contract/.../EventPayload.java:25-26`, `BaseEvent.java` — "consumers dedupe on this to stay idempotent"). Resolved 5 Oct 2026: the dedupe key is now `(event_id, consumer)` (migration `V<n>__processed_events_per_consumer.sql` in each of the nine services that has the table; the insert is `ON CONFLICT (event_id, consumer)`; the purge deletes by the pair), so one consumer's mark no longer stops another consumer from applying the same event. The mark-then-write-elsewhere case in reporting-svc's transfer path is fixed the same day (`applyTransferShippedOnce`), and purchase-svc's dropship raise is one transaction (`PurchaseRepository.raiseOnce`).
- **Golden rule #4 (discover via Consul, no hardcoded `host:port`) — also checked here, also claimed but unevidenced originally.** Every class under `client/` in every service resolves its target via `ConsulClient`/`ServiceRegistry.resolve(...)`; zero hardcoded `http://host:port` literals anywhere in `services/*/src/main/java` or `platform/*/src/main/java` (the only match for that pattern at all was a javadoc example in `ServiceInstance.java`).
- **Golden rule #5 (no secrets in code) — also checked here.** No hardcoded password/secret/API-key-shaped string literals anywhere in main Java source. Consistent with the original audit's finding that the gateway refuses to boot on a JWT secret under 32 chars (i.e. secrets are config-supplied, not defaulted in code).
- **Golden rule #9/#10 (thin controllers, DTOs don't expose domain) — CI-enforced in 8/12 services, gap closed in the other 4.** `shared/common-test/.../StoreQlArchRules.java` defines ArchUnit rules (`API_DOES_NOT_CALL_REPO`, `DTOS_DO_NOT_EXPOSE_DOMAIN`, `SERVICE_IS_HTTP_FREE`, `DOMAIN_IS_PURE`, `CONSUMERS_DELEGATE_TO_HANDLERS`) wired into a per-service `ArchitectureTest`. iam/tenant/product/inventory/pricing/order-svc had it; customer-svc ran the same rules inline in `CustomerIT`. **cart-svc, payment-svc, notification-svc, and reporting-svc did not** — manually checked each for an actual violation first (none found: no DTO imports `..domain..`, no `api/` class imports `..repo..` in any of the four), then added the missing `ArchitectureTest.java` to all four so a future regression fails CI instead of relying on manual discipline. All 20 checks (5 rules × 4 services) pass.
- **Telemetry refactor (`55c2a79`, landed same day as this audit, checked here since it wasn't covered originally).** Every service's traces+logs export path was consolidated from a direct Zipkin export plus a separate Promtail log-scraper onto a single OTLP path to `otel-collector` (`shared/common-web/.../OtelLoggingBridge.java` bridges `java.util.logging` into the OTel Logs API). Golden rule #12 is unaffected: health/liveness/readiness probes and the `helidon-microprofile-telemetry` dependency that wires tracing are untouched by the diff — only the export backend changed. The collector's new host binding (`127.0.0.1:4317`) is loopback-only, consistent with how Postgres/Redis are already exposed, so it doesn't weaken the "gateway is the only public door" claim above.

# Findings

### F1 — Broken object-level authorization on order reads (IDOR, PII leak) 🔴 High — ✅ FIXED
`GET /orders/{id}`, `GET /orders/{id}/history`, and `GET /orders/{id}/returns` scoped **only by tenant**, with no ownership check and no role gate (reads aren't covered by the write-only default-deny filter).

- **Evidence:** `services/order-svc/.../api/OrderResource.java:114` — `svc.getOrder(ctx.tenantId(), uuid(id))` → `OrderService.getOrder(UUID tenantId, UUID orderId)` (`service/OrderService.java:306`) filtered by tenant + id **only**. Compare `GET /orders/mine` (`OrderResource.java:77`) which correctly restricts to `customerId = ctx.userId()` — showing per-customer isolation is the intended model, and `/{id}` bypassed it.
- **Exposure:** the returned DTO carries `deliveryAddress`, `contactPhone`, `customerName`, `customerId` (`order-svc/.../dto/Dtos.java:46,228,231`). An authenticated `CUSTOMER` of a tenant could read another customer's order details by ID.
- **Mitigating factors:** order IDs are random UUIDv4 (not enumerable) and the leak is within a single tenant; a guest (no JWT) is blocked at the gateway. Exploitability was further narrowed by the token model: customer JWTs carry no tenant claim (`tenantId = null`), and the gateway strips client-supplied `X-Tenant-Id`, so a plain customer reaching `/{id}` resolved no tenant and got 404. The unguarded reads were still wrong as a standing invariant — safety rested on distant gateway/token details, not on the endpoint.
- **Fix (applied):** `OrderService.requireReadAccess` (mirrors `CartService.requireOwnership`): staff roles read any order in their tenant; a caller with a principal but no staff role must own the order (`order.customerId == ctx.userId()`), with denial as **404** (no existence oracle); a call with no principal at all (only `X-Tenant-Id`) is the service-to-service shape used by payment-svc's `OrderClient` and stays tenant-scoped. Enforced on all three reads via authorized service methods; covered by `OrderIT.orderByIdReadsAreObjectLevelAuthorized` (owner 200 / other customer 404 / staff 200 / s2s 200).

### F2 — God-files concentrate many aggregates in one class 🟠 Medium (maintainability) — ✅ FIXED (inventory-svc)
A handful of classes carry disproportionate size, mixing many aggregates and making review/merge risky.

- **Evidence (original):** `inventory-svc/.../repo/InventoryRepository.java` **3,935 lines**, `product-svc/.../repo/ProductRepository.java` **2,028** (down from 2,230 at the time this finding was first written — see below), `inventory-svc/.../service/InventoryService.java` **1,973**, `inventory-svc/.../api/AdminResource.java` **1,440**; bundled `Dtos.java`/`Domain.java` per service hold dozens of records.
- **Impact:** SRP erosion, hard to reason about locking/transaction scope, high merge-conflict surface. Not a runtime bug.
- **Partial progress noted when this finding was updated pre-fix:** `product-svc/.../repo/BrandRepository.java` (117 lines) and `CategoryRepository.java` (125 lines) were already extracted from `ProductRepository`, exactly the pattern this fix recommends.
- **Fix (applied to inventory-svc, the biggest offender):**
  - **Repository layer:** `InventoryRepository.java` split from 3,935 → **1,935 lines** (51%). 12 new aggregate repositories extracted (lot genealogy, thresholds, suggestions, demand history, cycle counting's CRUD, ABC analysis, safety stock, movements-read, physical inventory, reorder point/EOQ, kanban, costing/accounting-periods, lot actions, movement archive, picking-rules CRUD), joining 3 that already existed standalone (`PlanningConfigRepository`, `ReferenceDataRepository`, `SerialRepository`). What's left in the core is the genuinely tightly-coupled hot-path engine (receive/adjust/reserve/consume/deductSale/release, plus reads and mutations sharing its private locking/FIFO helpers `deductFifo`/`insertBatch`/`insertMovement`/`mapBatch`/`checkThresholdTx`) — splitting that further would mean extracting the shared locking logic itself into an injectable component, materially bigger and riskier than this fix's scope. One real bug caught mid-refactor: an early draft accidentally threaded `consumeTx`'s transaction connection into the picking-rule lookup, silently changing transaction semantics from the original (which used a separate connection via `query()`); caught by checking the base class and reverted to match original behavior exactly.
  - **Controller layer:** `AdminResource.java` split from 1,441 → **243 lines** (83%). 16 new `*Resource` classes, each still `@Path("/admin/inventory")` at the class level (JAX-RS routes on the combined class+method path, so this is safe) with its own `@Inject InventoryService`/`TenantContext` — no cross-file coupling at this layer since every method just delegates to the service. All 36 tests (including the full HTTP-level `InventoryIT` suite) pass, confirming zero route conflicts across the 17 resource classes.
  - **Not yet done:** `product-svc/ProductRepository.java` (2,028 lines) and `InventoryService.java` (2,029 lines, unchanged in size — only which repo it calls changed) remain unsplit.

### F3 — Residual fetch-all on low-cardinality admin lists 🟠 Medium-Low (scale-tail / consistency) — ✅ FIXED
The high-cardinality lists (orders, customers, products, inventory-levels) were cursor-paginated, but several admin lists returned the whole set with no `after`/`limit`.

- **Evidence (no cursor params):** `tenant-svc/.../api/AdminResource.java` `/staff` & `/stores` (and per-store `/zones`), `pricing-svc/.../api/PriceListResource.java` `/price-lists`.
- **Impact:** fine today (few stores/staff/price-lists per tenant) but inconsistent with the documented cursor convention and unbounded if a tenant grows large.
- **Fix (applied):** all four lists now use the standard keyset cursor (`(created_at, id)` ascending, `?after=&limit=`, `meta.nextCursor`), via new shared helpers in `common-web` `Cursor` (`decodeCreatedAtId` + generic `Page` builder) so the boilerplate isn't stamped per service. Consumers updated: the Flutter master-data providers (stores/zones/staff/price-lists) walk pages to completion through a new `core/network/paged.dart` helper (dropdown UX unchanged); product-svc's `PricingClient` default-list scan requests `limit=100`. The public `GET /storefront/stores` list is unchanged (separate surface). Covered by `OnboardingIT.adminListsAreCursorPaginated` (page walk, no duplicates, 400 on malformed cursor) and `PricingIT.priceListsAreCursorPaginated`.

### F4 — Inconsistent error surfacing in the Flutter client 🟠 Low
Structured API errors (`error.code`) are consumed by only a few screens; most still show the raw exception.

- **Evidence:** ~**36** raw `$e` / `.toString()` interpolations inside SnackBar/`Text` error paths across `lib/`, vs **4** files referencing the `api_error.dart` helper.
- **Impact:** users see framework/exception text; no machine-code-driven messaging or retry affordances; harder i18n.
- **Fix:** route all catch → snackbar paths through the `api_error.dart` helper (map `error.code` → localized message).

### F5 — Web build stores the auth token in plaintext localStorage 🟡 Low (accepted trade-off, worth hardening)
`lib/core/storage/app_storage.dart` uses OS Keychain/Keystore on native but **SharedPreferences (plain `localStorage`) on web** — a deliberate, well-documented choice (flutter_secure_storage's web backend needs a secure context and is itself plaintext under the hood).

- **Impact:** on the web shell the JWT is readable by any script in the origin → XSS becomes token theft. Acceptable given the constraint, but the risk should be bounded.
- **Fix:** pair with a strict CSP on the served UI, keep access-token TTL short with refresh rotation (a single-flight refresh already exists), and avoid persisting refresh tokens on web if feasible.

### F6 — Many published domain events have no consumer 🟢 Low (observation)
The outbox publishes a broad set of events; a large subset has no subscriber today.

- **Evidence:** consumers exist for user-registered, order confirmed/fulfilled/returned/cancelled, payment captured/failed/refunded, stock + sales events, tenant-created, staff-assigned, goods-received, order-placed, shortage-alert. **Unconsumed** include `kanban-*`, `lot-*`, `serial-*`, `move-order-*`, `accounting-period-*`, `price-changed`, `promotion-*`, `product-*`/`variant-created`, `store-credit-*`, `loyalty-*`, `zone-created`, `user-role-granted`.
- **Impact:** these are mostly legitimate future/audit hooks, but they add outbox+Kafka traffic for no reader. No correctness issue.
- **Fix:** none required; optionally annotate intent so they aren't mistaken for half-wired features.

### F7 — Frontend test coverage is thin 🟢 Low
Backend has a reasonable Testcontainers spread (49 files, 2–8 per service); the Flutter app has **11 test files for 98 Dart files**, concentrated on storefront checkout/catalog logic.

- **Impact:** admin/POS screens and most providers have no widget/golden/provider tests; regressions in those surfaces ship unguarded.
- **Fix:** add provider-level tests for the paginated list notifiers and golden/widget tests for the main admin & POS screens (the harness already exists).

### F8 — Same object-level authorization gap as F1, unswept, in customer-svc 🔴 High — ✅ FIXED
F1 fixed the missing per-record ownership check on order reads but never checked whether the identical shape existed elsewhere. It did: `GET /customers/{id}`, `/addresses`, `/loyalty`, `/loyalty/ledger`, and `/store-credit` were scoped **only by tenant**, with no ownership check and no role gate — the exact pattern F1 condemned in order-svc.

- **Evidence:** `services/customer-svc/.../api/CustomerResource.java:80-86,127-136,161-168,200-210,214-223` — each handler called `service.<method>(tenantId, customerId)` with no check that `customerId` belonged to the caller. `requireOwnership`/`requireReadAccess` (the pattern F1 introduced) existed in exactly two places pre-fix: `CartService.java` and `OrderService.java` — grep for the pattern across all 12 services confirmed customer-svc was not among them.
- **Exposure:** the returned DTOs carry address lines, loyalty point balance/ledger, and store-credit balance (PII + financial data). An authenticated `CUSTOMER` of a tenant who obtained another customer's UUID could read all of it.
- **Mitigating factors (same shape as F1):** traced the gateway's `isStorefrontCustomer` whitelist (`JwtAuthFilter.java:211-222`) — customer-svc paths are not on it, so a bare customer JWT (`tenantId` always null for customer accounts, confirmed at `AuthService.java:38`) cannot resolve a tenant on these paths today and got no tenant header at all, not a leak. Exploitability was narrowed by the same distant gateway/token detail F1 flagged as an insufficient basis for safety — "wrong as a standing invariant" applies here verbatim.
- **Fix (applied):** `CustomerService.requireReadAccess` (mirrors `OrderService.requireReadAccess`): staff roles (`PLATFORM_ADMIN`/`OWNER`/`MANAGER`/`STOREKEEPER`/`CASHIER`) read any customer in their tenant; a caller with a principal but no staff role must own the record (`customerId == ctx.userId()`), with denial as **404** (no existence oracle); a call with no principal at all (only `X-Tenant-Id`) is the service-to-service shape used by `notification-svc`'s `CustomerClient.emailOf` and `payment-svc`'s `CustomerClient.redeemStoreCredit`, and stays tenant-scoped. Enforced via new ctx-aware overloads (`get`, `listAddresses`, `getLoyaltyAccount`, `getLedger`, `getStoreCredit`) used only by the five read endpoints; the pre-existing 2-arg overloads are unchanged and still back the write paths (already covered by `AdminAuthorizationFilter`'s write default-deny). Covered by `CustomerIT.customerReadsAreObjectLevelAuthorized` (owner 200 / other customer 404 / staff 200 / s2s 200, across all five endpoints).
- **Open question this raises:** how many other services have the same shape that hasn't been checked yet? Followed up as F9 (payment-svc) and closed for purchase-svc (below).

### F9 — Same gap, one hop indirect: payment-svc read endpoints 🔴 High — ✅ FIXED
Continuing the sweep F8 started: `GET /payments/{id}`, `GET /payments/by-order/{orderId}`, and `GET /payments/by-order/{orderId}/refunds` had the identical missing-ownership-check shape. Unlike orders/customers, a `PaymentTender` doesn't carry the buyer's identity directly — only `orderId` — so ownership has to be resolved one hop away via order-svc.

- **Evidence:** `services/payment-svc/.../api/PaymentResource.java:69-113` — `get`, `listByOrder`, `listRefunds` all called `svc.<method>(ctx.requireTenantId(), id)` with no ownership check.
- **Exposure:** tender/refund DTOs carry amount, method, and reference — financial data, not just PII. Same mitigating factor as F1/F8: `GET /payments/{id}` etc. aren't on the gateway's `isStorefrontCustomer` whitelist (only `POST /payments/online` is), so a bare customer JWT can't resolve a tenant here today. Same "wrong as a standing invariant" reasoning applies — and this endpoint is one whitelist-entry away from becoming reachable, since a payment receipt view is an obvious next feature for the storefront.
- **Fix (applied):** `PaymentService.requireReadAccess(tenantId, orderId, ctx)` — staff read any payment in their tenant; a caller with a principal but no staff role must own the *order* the payment was captured against, resolved via the existing `OrderClient.getOrder` (the same s2s call payment-svc already makes to verify online-payment claims — golden rule #1, never trust a caller-supplied customerId, ask the owning service); a no-principal (tenant-only) caller keeps working for `notification-svc`/other internal callers. Denial is 404. Enforced via new ctx-aware overloads of `getTender`, `listTendersByOrder`, `listRefundsByOrder`, wired into the three GET handlers; write paths are untouched. Covered by six new cases in `PaymentServiceTest` (owner 200, non-owner 404, staff skips order-svc call, s2s skips order-svc call, both list endpoints enforce the same check) — unit-level rather than HTTP-level because payment-svc's existing test suite has no HTTP-integration harness (it drives `PaymentService` directly throughout), so this follows that file's established pattern (fake `OrderClient`/`PaymentRepository` via anonymous subclasses) rather than introducing a new one.
- **purchase-svc, checked and closed:** no `customerId` or customer-facing resource exists anywhere in purchase-svc's API layer (purchase orders, suppliers, intercompany invoices, goods receipts are all staff/B2B-only) — the F1/F8/F9 shape (an authenticated customer reading another customer's private record) has no analog there. No fix needed.
- **Rest of the sweep, checked and closed:** iam-svc (`/auth/me` is inherently self-scoped — no path param, no `GET /users/{id}`), tenant-svc, product-svc, inventory-svc, notification-svc, reporting-svc have no `customerId`-shaped endpoint at all. cart-svc already had the pattern (`CartService.requireOwnership`) before this audit.
- **Separate observation surfaced while reading this file for F9 (not a new finding, not fixed — flagging since it wasn't mentioned anywhere in the original audit despite sitting in the same class the audit read):** `PaymentResource.java:49` carries a first-party TODO — `payOnline` "still self-attests that money actually moved," i.e. online payment capture has no real payment-provider integration yet. This is a product-completeness gap, not a bug in what exists; no action taken here.

### F10 — Missing role gate on a staff-only read (different shape, found while sweeping for F1/F8/F9) 🟢 Low — ✅ FIXED
While sweeping the remaining services, `pricing-svc`'s `GET /customer-vat-status/{customerId}` turned up with no role check at all. This is **not** the F1/F8/F9 object-ownership shape — VAT status is B2B tax data staff maintain about business accounts, with no individual customer JWT that could ever be its "owner" (no storefront path resolves a tenant here for a customer token, and nothing else in the codebase calls this endpoint). It's the same root cause F1 named on day one though: reads aren't covered by `AdminAuthorizationFilter`'s write-only default-deny, so an endpoint that doesn't add its own gate has none.

- **Evidence:** `services/pricing-svc/.../api/CustomerVatStatusResource.java:39-44` (pre-fix) — `get` called `svc.getCustomerVatStatus(ctx, customerId)` straight through, tenant-scoped only.
- **Fix (applied):** `ctx.requireAnyRole("PLATFORM_ADMIN", "OWNER", "MANAGER", "STOREKEEPER", "CASHIER")` added to the GET handler — the same `STAFF_ROLES` set `AdminAuthorizationFilter` already uses for generic writes, so read and write access are symmetric. Covered by `PricingIT.customerVatStatusReadRequiresAStaffRole` (no role → 403; staff role → 200).

### F11 — Layering/DTO-boundary rules unenforced in 4 of 12 services 🟢 Low — ✅ FIXED
Found while verifying golden rule #10 (never expose domain entities over HTTP), which the original audit's Method line claimed to have checked but never showed evidence for. `shared/common-test/.../StoreQlArchRules.java` defines the ArchUnit rules that make this a CI-enforced invariant rather than a review-time hope; 8 of 12 services wire it into an `ArchitectureTest`, but `cart-svc`, `payment-svc`, `notification-svc`, and `reporting-svc` didn't.

- **Evidence:** `grep -rl StoreQlArchRules services/*/src/test` matched 8 services (or, for customer-svc, an equivalent inline check in `CustomerIT`); those four had none.
- **Checked for an actual violation before treating this as just a coverage gap:** none found in any of the four — no class under `dto/` imports `domain/`, no class under `api/` imports `repo/`.
- **Fix (applied):** added `ArchitectureTest.java` to all four services, wiring the same five rules (`API_DOES_NOT_CALL_REPO`, `SERVICE_IS_HTTP_FREE`, `DOMAIN_IS_PURE`, `CONSUMERS_DELEGATE_TO_HANDLERS`, `DTOS_DO_NOT_EXPOSE_DOMAIN`) the other services already run. All 20 checks (5 rules × 4 services) pass, so a future regression now fails CI instead of depending on manual discipline.

### F12 — `@Valid` missing on nested list DTOs: item-level Bean Validation was silently dead code, including on order placement 🟠 High — ✅ FIXED
Found while verifying golden rule #15 (validate every input at the boundary). A systematic check of every `@POST`/`@PUT` endpoint taking a `*Request` DTO surfaced two distinct problems, both about Bean Validation constraints existing on paper but never actually firing.

**Problem 1 — 6 endpoints never called `Validations.validate()` at all**, so their DTO's own field-level constraints (`@NotBlank`, `@NotNull @Positive`) were completely unenforced:
- `OrderResource.cancel` / `LayawayResource.cancel` — `VoidRequest.reason` is `@NotBlank`, but a request body with `{"reason":""}` sailed through untouched.
- `PriceListResource.batchUpsertItems` — had a manual null/empty check on the outer `items` array but never validated each `UpsertPriceListItemRequest` (`@NotBlank variantId`, `@NotNull @Positive price`, `@NotNull @Positive minQty`) — a batch item with a **negative price** would silently upsert.
- `inventory AdminResource.receiveBatch` — same shape: `BatchReceiveItem.qty` is `@NotNull @Positive` but unchecked.
- `product AdminResource.addCategorySetMember` / `assignVariantCategorySet` — `@NotBlank` id fields unchecked; a blank id would proceed to `UUID.fromString("")`, which throws `IllegalArgumentException` — likely surfacing as an uncaught 500 rather than a clean 400.
- (`importSupplierCsv` was also flagged by the initial automated sweep but turned out to already have an equivalent manual `req.csv().isBlank()` check — false positive, not fixed, noted here so the sweep's own accuracy is auditable.)

**Problem 2 — a deeper, wider issue: even where `Validations.validate(req)` *was* called, it doesn't cascade into list elements without `@Valid` on the list field itself** (Jakarta Bean Validation requires this explicitly). 13 nested-list fields across 5 services had `@NotNull List<XxxRequest>` with no `@Valid`, so the per-item constraints on those nested types were dead code even on endpoints that looked correctly guarded:
  - **order-svc** (most critical — this is checkout): `PlaceOrderRequest.items` (`OrderItemRequest`: `@NotBlank variantId`, `@NotNull @Positive qty`), `CreateReturnRequest.items`, `CreateLayawayRequest.items`, `CreateSpecialOrderRequest.items`.
  - **inventory-svc**: `BatchReceiveRequest.items`, `CreateMoveOrderRequest.lines`, `CreateTransferOrderRequest.lines`, `BatchReserveRequest.reservations`, `SetZonePrioritiesRequest.zonePriorities`.
  - **pricing-svc**: `BatchUpsertPriceListItemsRequest.items`. **purchase-svc**: `CreateGoodsReceiptRequest.lines`. **product-svc**: `ImportProductRequest.variants`.
- **Exposure, traced concretely for the worst case:** `POST /orders` is reachable by a bare customer JWT with no staff role (it's on the gateway's `isStorefrontCustomer` whitelist — see F1). Before this fix, that customer could place an order with `"qty": 0` or a negative quantity, and it would pass `OrderResource.place`'s `Validations.validate(req)` call cleanly (the `@NotNull` on `items` passed; nothing checked inside each item). Checked for a compensating check elsewhere: `OrderService.java` has no manual qty/price check (only a null-check on `unitPrice` for pricing-mode selection), and `order_items` in `V1__init.sql` has no `CHECK` constraint on `qty`. So a malformed item from the **least-trusted principal in the system** would have proceeded all the way to persistence with zero enforcement at any layer.
- **Fix (applied):** added `@Valid` alongside the existing `@NotNull` on all 13 list fields (cascades into each element's own constraints); added the 5 real missing `Validations.validate()` calls; for `batchUpsertItems` specifically, validation was added **inside the per-item loop in `PricingService.batchUpsertPriceListItems`** rather than as a blanket resource-level call, because the endpoint's documented contract is "never 4xx on partial failure" — an invalid item must become a per-item entry in `BatchUpsertResult.errors`, not a whole-batch rejection. All fixes are purely additive (tightening validation that was already declared as intended) — verified zero regressions by running the full existing test suites for all 5 touched services (117 tests, 0 failures) before adding new coverage.
- **New tests (5, all passing):** `OrderIT.placeOrderRejectsNonPositiveItemQty`, `OrderIT.cancelRejectsABlankReason`, `InventoryIT.batchReceiveRejectsNonPositiveItemQty`, `PricingIT.batchUpsertItemsRejectsAnInvalidItemButStillUpsertsTheRest` (proves the partial-success contract: 200, `upserted:1`, bad item named in `errors`), `CatalogIT.categorySetMemberAndAssignmentEndpointsRejectBlankIds`.
- **Not fixed, flagged for follow-up:** `BulkImportRequest`/`ProductService.bulkImport` (JSON bulk catalog import) has the same missing-`@Valid` shape on `categories`/`products` and likely implements its own per-item partial-success pattern (it returns a `BulkImportResult` with an `errors` list, same shape as the pricing batch endpoint) — fixing it properly means reading and safely modifying that import pipeline's per-row logic, which is a larger, riskier change than the mechanical fixes here. `ImportProductRequest.variants` already got its `@Valid` added (harmless either way), but the service-layer per-item validation call was not added.
