## Problem

The catalogue is where mistakes are cheap to make and expensive to find:

- **Images are stored as uploaded.** The server only refuses anything of 256 KB or more, so the admin app has to shrink each picture, another client cannot, and the storefront downloads the full image for a small tile. There is one image per product, so there is no gallery, and therefore nothing for a plan to count.
- **Duplicates are found one write at a time.** The same GTIN under two SKUs is refused when typed, but a business that imported years of data before the rule, or that has near-copies (same name and pack under two codes), has no way to see them.
- **A category can be moved without a trace.** Who put "Frozen" under "Bakery", and when, is not recorded; the row keeps only its last `updated_at`.
- **Range reviews and planograms have no screen.** The API can draft a review, decide keep/introduce/delist per line, publish a planogram and complete a reset, but the admin app only shows fixtures and the range changes that are due.
- **An unreachable code.** The service can say `PRODUCT_IMAGE_TYPE_INVALID`, but the endpoint declares the three image types it consumes, so JAX-RS answers `415` first and the code never reaches a client.
- **A laxer age rule needs a reason.** Setting an age restriction below the business's policy floor is refused, but a decision to tighten or relax carries no recorded reason.

## Outcome

- A picture is uploaded once and the server makes the sizes the shop needs; a product can hold several images in an order up to a limit the plan sets.
- A manager can run a duplicate report and see the SKUs, barcodes and near-copies to merge or retire.
- Every category move shows who, when, from where and to where.
- A range review and a planogram can be done in the admin app.
- A wrong image type answers with the code the API promises; the age-restriction change says why.

## Already there

- Cycle refusal on a category move (`409 PRODUCT_CATEGORY_CYCLE`, a parent from another business `400 PARENT_NOT_FOUND`), racing re-parents (`CategoryTreeTest`, `CatalogGuardsIT.aCategoryCycleIsRefused`, `.racingReparentsCannotCreateACycle`, `.categoriesDoNotCrossBusinesses`).
- Named duplicates at write time: `409 PRODUCT_SKU_DUPLICATE` / `PRODUCT_BARCODE_DUPLICATE` on create, update and import (`VariantDuplicateCodeTest`, `CatalogGuardsIT.duplicateSkuAndBarcodeAreNamed`); a GTIN-shaped barcode must carry a valid check digit, `400 PRODUCT_BARCODE_INVALID` (`VariantBarcodesTest`, `CatalogGuardsIT.aGtinShapedBarcodeIsCheckedOthersAreNot`).
- A delisted variant does not scan (`CatalogGuardsIT.aDelistedVariantDoesNotScan`); the lifecycle catalogue's CAT-07 gap was stale.
- Image boundaries: exactly 256 KB is `400 PRODUCT_IMAGE_TOO_LARGE`, empty `400 PRODUCT_IMAGE_EMPTY`, another business's product `404` (`CatalogGuardsIT.imageBoundaries`); the byte plan cap `images.mb.max` (`ImageStorageCapIT`, `PlanIT`).
- The range and planogram rules on the server (only one draft per fixture, publish supersedes, own-brand delist needs a note, close produces a `RangeOutcome`, OWNER/MANAGER on every write): `MerchandisingIT`, `AssortmentIT`, `AssortmentTest`, `MerchandisingTest`.
- **Screens, partly:** the Shelf space screen (`frontends/storeql-app/lib/features/admin/shelf_space_screen.dart`, `shelf_space_screen_test.dart`) already lists fixtures and the range changes that are due. The catalogue's "no screen found" is therefore only true for reviews, clusters, planogram positions and publish, and resets.
- The per-product image count is moot today only because a product holds one image; it matters once slice 2 lets it hold several.

## Who and where

- **Personas** ([PRD §2](../PRD.md)): the **catalogue manager** and **range/merchandising manager** (all of it), the **owner** (plan, approvals), the **shopper** (sees the sizes).
- **Channels:** back office; the storefront reads the image sizes.
- **Scope:** per business; range clusters and planograms per store cluster and fixture as they are.
- **Roles that can write:** OWNER, MANAGER (STOREKEEPER for images and the duplicate report's read, as today); reading the report needs management.
- **Sandbox tenant:** behaves the same.

## Scope

- **In**, in build order (each slice ships on its own):
  1. **Small fixes (product-svc).** (a) The image endpoint accepts any content type and the service checks it, so a non-image answers `400 PRODUCT_IMAGE_TYPE_INVALID` as documented (the content is also sniffed by its first bytes, so a text file sent as `image/png` is refused the same way). (b) An age-restriction setting that departs from the business's own policy floor carries a **reason** (`400 PRODUCT_AGE_RESTRICTION_REASON_REQUIRED`), kept with who and when, in the existing age-restriction record; a change is refused today only for a laxer number and that stays.
  2. **A category move is on the record (product-svc).** `category_moves` (append-only): category, old parent, new parent, actor, at. Written on the same transaction as the update in `updateCategory` only when the parent actually changes. `GET /admin/categories/{id}/history` (management, cursor) and a "History" action on the Categories screen. Renames keep `updated_at` only.
  3. **The duplicate report (product-svc).** `GET /admin/catalogue/duplicates` (management, cursor) returns groups: **same barcode under different SKUs across products' variants that predate the unique rule** (kept for data loaded before it, and any that slipped through), **same SKU differing only in case, spaces or punctuation** (a normalised comparison), and **near-copies**: same brand, same normalised name and the same measure under different products. "Near" is fixed by that stated rule, no fuzzy threshold to tune; each group names the products and variants and their status. The report only reads; nothing is merged or deleted here (a merge is a person's act with today's edit and delist). Screen: Admin → Products → "Duplicates" with links to each item.
  4. **Server-made image sizes (product-svc).** On upload the server decodes the image (JPEG, PNG; WebP through a decoder library added once in the parent pom's managed versions, per the dependencies rule) and stores the original (still under the 256 KB ceiling for the upload) plus a **thumbnail and a card size**, each with its own bytes and content type in `product_image_sizes` (append-only replace-by-delete of the whole set on a new upload, in one transaction). `GET /catalog/products/{id}/image?size=thumb|card|full` serves the size, defaulting to `full`; long cache headers with the image's version. The size widths are platform settings tied to the storefront layout, not business policy. An image that cannot be decoded is `400 PRODUCT_IMAGE_UNREADABLE`. The admin app keeps its own compression (a smaller upload is faster) but the server no longer depends on it. The storefront tile requests `thumb`, the product page `card`.
  5. **A gallery and a per-product image count limit (product-svc, tenant-svc).** A product may hold several images in an order: `product_images` moves from one row per product to a numbered set (`position`, one marked primary); the existing single-image routes keep meaning "the primary image". `POST /admin/products/{id}/images`, `PUT …/images/order`, `DELETE …/images/{imageId}`. A new plan entitlement `images.per-product.max` is added to `Plans.CATALOGUE` **with the refusal that enforces it, in product-svc** (the service that owns what is counted), through `Entitlements`: the ceiling is the plan's and is unlimited until a plan sets it (`409 PLAN_LIMIT_REACHED` naming the key, as products and megabytes do). The existing byte cap `images.mb.max` still counts every image and size's original bytes (derived sizes are not counted against a plan; they are the platform's cost of serving). Fail open when the plan is unreadable, as every limit does.
  6. **Range reviews and planograms in the admin app (Flutter).** Extend the Shelf space screen (or its neighbours under Admin → Inventory or Products): **Clusters** (create, add stores), **Reviews** (start, add lines with figures, decide KEEP/INTRODUCE/DELIST per line, the own-brand delist note field, close showing the `RangeOutcome` with what was left alone and why, abandon), **Planograms** (fixture, draft, set facings with a live shelf-capacity meter, publish showing which prior one it supersedes), **Resets** (schedule, complete). Every server refusal shown in words (`status_labels.dart`), the shell's adaptive widgets used (UI-GUIDE §7.2). No new server rule.
- **Out, on purpose:**
  - **Approval of a delist of a fast-moving line, or of a review that delists many own-brand lines at once.** One mechanism on the approvals page (action keys `catalog.discontinue` and `catalog.range-review-close`, which the approvals catalogue adopted as written; this page first spelled them `catalogue.delist-fast-moving` and `catalogue.bulk-delist`). This page adds only the range screen where the approval is asked for.
  - **Merging duplicates automatically.** The report finds; a person decides (a merge moves stock, prices and history across services).
  - **An object store or CDN.** Bytes stay in Postgres (the design comment on `product_images`); the sizes make that affordable and a CDN is an infrastructure choice.
  - **Video, 360 views or documents.** Images only.
  - **Recall `source` naming only two regulators.** A separate known follow-up (memory: recall-source-uk-only), in inventory-svc's recall data, not this page.
  - **Editing category names with history.** Only a move (a change of parent) is recorded; a rename keeps `updated_at`.

## Data and flow

- **Owned by product-svc:**
  - `category_moves` (new, append-only): id, tenant, category, from_parent, to_parent, actor, at; index on tenant first.
  - `product_image_sizes` (new): image id, size (`THUMB`, `CARD`), content type, bytes, width, height.
  - `product_images` gains `id`, `position`, `is_primary`, `version`; existing rows become position 0 and primary. The 256 KB check and `tenant_id` first index stay.
  - `age_restriction_reasons` or a `reason` on the existing age-restriction record: reason text, actor, at.
  - No new table for the duplicate report: it is a read over `variants` and `products`.
- **Owned by tenant-svc:** the `images.per-product.max` entry in `Plans.CATALOGUE` (owner listed as product-svc) and the plan-grant editing that already exists.
- **Needs from other services:** `Entitlements` (a cached read of the plan's allowances) in product-svc; nothing else. No joins.
- **Events published:** none new. The existing product/variant events are unchanged (a gallery does not change what others need; `ProductImageChanged`, if the storefront cache already listens to one, keeps firing on any primary-image change).
- **Retryable writes (Idempotency-Key):** the image uploads (a replay adds no second image: the key names the upload).
- **New error codes:** `400 PRODUCT_IMAGE_UNREADABLE`, `409 PLAN_LIMIT_REACHED` (existing code, new key `images.per-product.max`), `400 PRODUCT_AGE_RESTRICTION_REASON_REQUIRED`, `404 PRODUCT_IMAGE_NOT_FOUND` (existing), `400 PRODUCT_IMAGE_TYPE_INVALID` (now reachable).

## Money, time and limits

- **Currency:** none.
- **Ledger postings:** none.
- **Dates:** all UTC; move times and reasons in `timestamptz`.
- **Plan limits:** `images.per-product.max` (product-svc refuses; unlimited until set) next to the existing `images.mb.max`. No number is chosen by the platform.

## Constraints

- Golden rules 1 (no cross-service tables), 3 (tenant from the JWT, first condition on every query), 8 (the move log is append-only), 9 and 10 (thin resources, DTOs), 15 (validate input; the type check is by sniffing as well as the header).
- Images are read back in full by the storefront: the size a tile asks for must be the small one, or the change does nothing for shoppers. Long-lived cache headers stay; the version in the address keeps them right.
- Dependencies rule (CLAUDE.md 22.11): a WebP decoder is added once in the parent pom with its advisory checked (`scripts/vuln-scan.sh deps`), never pinned in the module.
- Existing tenants: existing images become a primary image with sizes made lazily on first read (a small job backfills them); no upload path changes for a client that sends one image.

## Decisions

<!-- Filled while building. -->
- **2026-10-02, a new product of a manager held to stores is never sold at every store:** the stores it names must all be theirs (`403 STORE_ACCESS_DENIED`; `POST /admin/products` gains an optional `storeIds`, written on the product's own transaction), and naming none it is ranged to all the stores they are held to (from their sign-in, not asked of tenant-svc) rather than refused; an owner or a manager of the whole business still creates one sold everywhere. A product with no `product_stores` rows is on every shelf, and store-level staff's new items are local items ranged to their own sites, as retail systems treat store-originated items. Defaulted rather than refused because the admin app's product form sends no stores, and a refusal there ("That is not one of your stores.") could not be acted on; one rule (`CatalogueStores.rangeOfNew`) serves the form and both imports.
- **2026-10-02, an import judges where a row's product is sold row by row, as the catalogue stands.** A store that is not the business's or not the caller's is still refused for the whole sheet (it shows the sheet was made for someone else); a held caller's new product naming no store is ranged to their stores, as at `POST /admin/products`; a `REPLACE` row that would narrow a product sold everywhere is that row's error (`BUSINESS_WIDE_ONLY: …`), nothing of the row written, because it depends on what the business already holds and the importer is lenient by design.
- **2026-10-02, `REPLACE` adds a row's stores to the product it finds by the same rule as the PUT** (`CatalogueStores.requireAdditionHeldTo` over the range as it would stand): an owner's row may still range a product sold everywhere to the stores it names; a held manager's may add only theirs, and never turn "every store" into theirs.
- **2026-10-02, a supplier sheet's rows are not ranged to the destination store by default.** Quietly ranging rows to where the stock lands would narrow a product nobody chose to narrow; a row with no Store is sold at every store, or, for a held manager, at all the stores they keep (the rule above), never at the destination store alone.
- **2026-10-02, a range change is decided inside the transaction that writes it,** against the stores read there with the product row locked (`FOR UPDATE`), for the PUT and the import alike: two changes to one product are serialised and each is judged on what the other left.
- **2026-10-02, one check that a store is the business's** (`CatalogueStores.requireOwn`), used by the catalogue and the range alike; each door keeps its refusal on the wire (`PRODUCT_STORE_NOT_FOUND`, `ASSORTMENT_STORE_NOT_FOUND`).
- **2026-10-02, a supplier import's stock receipt stops at the first call inventory-svc does not answer** and reports that call's lines and every later line, with the reason; the client throws it so its circuit breaker counts it, and it is never retried, because inventory-svc's batch receive takes no idempotency key and a call that timed out may have landed (a timed-out call is reported as "may not have been received", not as "not received").
- **2026-10-02, money in product-svc is held to its currency's own minor units** (ISO 4217 via common-service `Fx.minorUnits`): a supplier sheet's price with more decimals than its currency has, or below zero, is not set and is named by SKU in `priceErrors`; a review line's revenue or margin with more is `400 REVIEW_LINE_FIGURES` and an unknown currency `400 REVIEW_LINE_CURRENCY`; neither is rounded into a figure nobody wrote. `range_review_lines.revenue/margin` widen to `NUMERIC(18, 4)` (V29; the most minor units ISO 4217 gives) and are written back at the currency's own units. Kept fixed on purpose: shelf shares (4 decimals, a fraction), dimensions, weights, measures and UoM factors (not money), GS1 amounts (their decimals come from the AI), and the variant attribute `tradePrice` (the supplier's text as written).
- **2026-10-02, moving a product to or from "every store" is refused a held manager as `403 BUSINESS_WIDE_ONLY`, not `STORE_ACCESS_DENIED`** (the PUT, a `REPLACE` row, the range-change door): the store in question is usually theirs, so "That is not one of your stores." would not say what is wrong; `BUSINESS_WIDE_ONLY` is the platform's code for what needs a caller held to no store, and the app already words it ("Only an owner or a head-office manager can do this.").
- **2026-10-02, the range-change door (`POST /admin/assortment/changes`, `…/reviews/{id}/close`) holds a manager held to stores to the same rule as the PUT, when the change is recorded:** the line must be the business's (`404 PRODUCT_NOT_FOUND`, which also stops another business recording a change against our product id); a cluster is never theirs to aim at (`403 BUSINESS_WIDE_ONLY`) — not only one holding a store they do not keep, because membership is read on the day a change applies and a cluster wholly theirs today may hold other stores by then, and clusters are head-office planning in retail practice; and a line sold at every store, or a change that would leave it at none, is `403 BUSINESS_WIDE_ONLY`. A closing review that would produce such a change is refused whole and stays open (closing it with part of its decisions quietly set aside would leave a record of changes that never happen). Every assortment door now checks the store as the catalogue does — the business's first (`404 ASSORTMENT_STORE_NOT_FOUND`), then the caller's (`403`) — where it used to answer a held manager `403` for another business's store.
- **2026-10-02, a range change is re-judged when it is applied, on the range read in the applying transaction with the product row locked** (`AssortmentRepository.apply`): a change keeps whether its maker was held to stores (`assortment_changes.held_to_stores`, V30; older rows read as business-wide, as they were applied until now), and a held manager's LIST of a line that has since become sold everywhere is not applied (`BUSINESS_WIDE_ONLY`) and stays due. For anyone, a DELIST that would leave a line at no store is not applied (`ASSORTMENT_LAST_STORE`) and stays due: no rows means every store, the opposite of a de-list; discontinuing the line is how it stops being sold anywhere. Both follow the sweep's rule that what cannot be written as it reads is refused loudly rather than guessed.
- **2026-10-02, a supplier sheet's price is sent to pricing-svc at its currency's own scale and kept there:** pricing-svc's V16 (same round) widens `price_list_items.price`/`applied_prices` to unconstrained `NUMERIC` and refuses a list price finer than the list's currency, so a KWD 12.345 is no longer rounded to 12.35 on the way in; product-svc's check and pricing-svc's ship together.
- **2026-10-02, a supplier import's prices stop at the first call pricing-svc does not answer,** as its stock receipt does: that call's rows and every later row are reported in `priceErrors` with a plain reason (never an exception's own words), and `PricingClient` throws `Unreachable` so its circuit breaker counts the failure (swallowed, a dead pricing-svc never opened it); an open breaker reports every row as not asked. Its `@Retry` is removed: a retry re-sent every chunk from the first, writing price history and `PriceChanged` again, and waited out the 30-second read timeout up to three times inside the import. An answer to "your price lists" that is not a list (a refusal, a failure, unreadable words) sets nothing and **makes no list**: it used to be read as "there is none" and a second Default list was made beside the business's own.
- **2026-10-02, a supplier sheet's quantity or price must be a plain number** — optional sign, digits, a point before any decimals, at most 18 digits either side — or it is not received / not set and is named by SKU in `stockErrors` / `priceErrors` ("is not a plain number (digits and a decimal point only)"). Never guessed: `12,345` is a decimal comma in one country and a thousands separator in another (location-neutral), and a currency sign, code or spreadsheet exponent is refused the same way (an exponent is also what would let one cell cost more than the row). A price that cannot be read sets nothing, so it asks no `pricing.write` and no pricing-svc. The variant's attributes keep what the supplier wrote: `caseSize` a number where it reads as one and otherwise the text, `tradePrice` always the text, both written as JSON that reads — the digits are no longer picked out ("12 x 6" was 126, "-5" was 5, "abc" broke the JSON and lost the variant under "check SKU uniqueness") and quotes no longer stripped.
- **2026-10-02, `POST /admin/products` judges the request before its stores:** a brand or category id that is not a UUIDv7, the status, `launchOn`, the safety information and the listing rules (400) come first, then the stores it names (404, then 403), then the plan (409), then the write — a wrong request is told what is wrong with it, not whose stores they are, and tenant-svc is not asked about stores for a request that will be refused anyway.
- **2026-10-02, a de-list that would leave a line at no store is refused when it is recorded, by anyone** (`409 ASSORTMENT_LAST_STORE`, `POST /admin/assortment/changes` and `…/reviews/{id}/close`), where it was recorded and then refused by every sweep, due for ever. Judged on the range **as planned for the change's day**: the range now, with the changes already recorded for that day or before applied as the sweep would apply them (a refused one moving nothing), so a planned swap — list at B, then de-list at A — is recorded. A closing review that would produce one is refused whole and stays open, naming the line (decide KEEP and discontinue it, or list it elsewhere first). A held manager gets the same 409, not `403 BUSINESS_WIDE_ONLY` as before: nobody can do it, so pointing them to a manager of the whole business sent them to someone who could not either; the refusal says what does stop a line being sold (discontinue it). The sweep keeps its `ASSORTMENT_LAST_STORE` for a range that changed after the change was recorded. A de-list of a line sold **everywhere** is still recorded and waits, due, for the line to be given a range (`ASSORTMENT_RANGED_EVERYWHERE`), as `AssortmentIT.cannotDelistWhatIsEverywhere` has it: that one the range can say once its stores are named. Held-manager refusals that remain name who can: "an owner or a manager of the whole business".
- **2026-10-02, a range change locks the product row `FOR NO KEY UPDATE`, not `FOR UPDATE`** (`ProductRepository.lockedStoresTx`, `AssortmentRepository.lockedRangeTx`): it conflicts with itself, so range changes to one product are still serialised and each judged on what the other left, but not with the `FOR KEY SHARE` a foreign-key check takes, so adding a variant (or another table's row referencing the product) is not held up behind a range change. The earlier decisions' "`FOR UPDATE`" reads as this lock. The product update's own lock (`updateProductWithOutbox`) is not a range change and is unchanged.
- **2026-10-02, V29's comment corrected before it shipped:** V27 kept review money at `NUMERIC(14, 2)`, twelve whole digits, so V29's `NUMERIC(18, 4)` adds two rather than keeping fourteen "as before". V29 is new this round, never committed or released, and applied only by the tests' fresh databases, so changing the file breaks no Flyway checksum; once released, a migration's text is never changed.
- **2026-10-02, a de-list the sweep finds would leave a line at no store is closed as refused, once, not left due** (`assortment_changes.refused_at`/`refusal_code`/`refusal_detail`, V31, with `ck_assortment_change_settled_once`: applied or refused, never both). Supersedes "stays due" for `ASSORTMENT_LAST_STORE` in the two entries above. The door cannot see everything that moves a range later: a change recorded afterwards for an earlier day, a listing that gives a waiting de-list of a line sold everywhere its last store, a store joining the cluster a de-list aims at, a PUT of the product's stores, an import. Such a de-list used to be refused by every hourly sweep, for ever. No range can make "take it out of every store it is sold at" apply as it reads, so the sweep closes it in the transaction that judged it. The product row is locked and the change re-read under the lock, so one another sweep has settled is left alone. It is reported once with `stillDue: false`, the line's history shows `refusedAt`, `refusalCode` and `refusal`, and it is never due again. The other refusals still wait (`stillDue: true`): `ASSORTMENT_RANGED_EVERYWHERE`, a held manager's `BUSINESS_WIDE_ONLY` and `CLUSTER_EMPTY`, because naming stores, narrowing the line again or filling the cluster still lets those apply.
